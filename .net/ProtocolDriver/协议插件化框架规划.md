> 目标：为工业通信系统设计一个**插件式协议框架**，包含：
> - **插件式协议框架主程序（Host）**：自动发现、动态加载、热更新、运行时管理

## 1. 概述
本规划为团队交付可运行的协议插件化平台提供详细设计：
- Host 以 .NET 8（或 .NET 6/7/8 均兼容）实现，负责插件发现、隔离加载、运行、热替换。
- 协议插件以独立 DLL（Assembly）形式发布，遵循统一接口，插件内部可依赖第三方库。
- 支持在 Docker / Kubernetes 环境中热刷插件（需结合卷挂载、或通过 API 上传覆盖）。

该方案既能覆盖寄存器类协议，也能支持复杂协议（S7、OPC UA）在插件内完全实现。

---

## 2. 设计目标与约束
### 目标
- 插件可无缝加入系统，不影响其它插件运行
- 支持热更新：替换插件后 Host 无需重启
- 支持跨平台运行（Windows / Linux / Docker / K8s）
- 简单、安全的插件上传/回滚流程
- 插件可以由第三方或客户开发并下发

### 约束
- 插件必须遵循 IProtocolDriver 接口
- 插件应尽量避免静态共享全局状态（便于卸载）
- Host 对插件执行有超时、资源限制与错误隔离机制

## 3. 总体架构

```
+-----------------------------------------------------------+
| Host Web App / API                                        |
|  - 管理界面 (上传插件 / 热更新 / 状态监控)               |
|  - Plugin Manager (发现/加载/卸载/回滚)                   |
|  - Transport Manager (TCP/UDP/Serial/CAN)                 |
|  - Sandbox & ACL                                          |
+-----------------------------------------------------------+
            |                     |                   
            | 协议DLL              | 插件输出数据
            v                     v
+----------------+   AssemblyLoadContext   +----------------+
| Plugin A.dll   | <----------------------> | Plugin B.dll   |
| (Modbus)       |                        | (S7)           |
+----------------+                        +----------------+

```

核心组件：
- **Transport Manager**：抽象通信通道（TcpClient/UdpClient/SerialPort/Can）并提供给插件
- **Plugin Manager**：负责插件生命周期、加载上下文管理、版本管理
- **Plugin Sandbox**：运行时资源/权限控制、异常隔离
- **Plugin API**：Host 提供给插件的运行时 API（日志、配置、持久化、metrics）

## 4. 协议插件接口规范（IProtocolDriver）

```csharp
public interface IProtocolDriver : IDisposable
{
    // 插件元信息
    string ProtocolName { get; }
    string Version { get; }

    // 初始化：Host 为插件注入运行时能力（logger, transport factory, config）
    Task InitializeAsync(DriverContext context, CancellationToken token = default);

    // 根据输入构造请求（二选一：同步/异步）
    byte[] BuildRequest(object requestModel);

    // 主动发起请求/执行命令（可能与 Transport 结合）
    Task<DriverResult> ExecuteAsync(byte[] request, CancellationToken token = default);

    // 从原始响应解析到统一数据结构
    DriverParseResult ParseResponse(byte[] response);

    // 可选：插件自身的健康检查
    Task<DriverHealth> CheckHealthAsync(CancellationToken token = default);
}

public record DriverContext(ILogger Logger, ITransportFactory TransportFactory, IConfiguration Config, IHostApi HostApi);
public record DriverResult(bool Success, byte[] Response, string? ErrorMessage = null);
public record DriverParseResult(string[] Tags, IDictionary<string, object> Data);
public record DriverHealth(bool IsHealthy, string Message);
```

**说明**：
- `IHostApi`：Host 提供给插件的 API（发布事件、写入数据库、上报 metrics）
- 插件实现应尽量使用 Host 提供的 TransportFactory，而不是直接 new 出 TCP 客户端以利于管理

## 5. 插件项目模板

### 5.1 项目结构（示例）
```
MyProtocol.Plugin/
  src/
    MyProtocol.Plugin.csproj
    Drivers/
      MyProtocolDriver.cs  // 实现 IProtocolDriver
    Models/
    README.md
  build/
  artifacts/
```

### 5.2 csproj 要点
- 目标框架：`net8.0`（或可选 `net6.0`）
- 输出单个 DLL（Optional: 发布为单文件）
- 不要引用 Host 程序的内部程序集（仅依赖 Host 定义的公共接口 nuget 包）

示例 PackageReference：
```xml
<PackageReference Include="Host.SDK" Version="1.0.0" />
```

### 5.3 插件初始化样例（MyProtocolDriver.cs）
```csharp
public class MyProtocolDriver : IProtocolDriver
{
    private DriverContext _ctx;
    public string ProtocolName => "MyProtocol";
    public string Version => "1.0.0";

    public async Task InitializeAsync(DriverContext context, CancellationToken token = default)
    {
        _ctx = context;
        _ctx.Logger.LogInformation("MyProtocol initialized");
        // 可从 context.Config 读取插件配置
    }

    public byte[] BuildRequest(object requestModel) { /* ... */ }
    public async Task<DriverResult> ExecuteAsync(byte[] request, CancellationToken token = default) { /* ... */ }
    public DriverParseResult ParseResponse(byte[] response) { /* ... */ }
    public Task<DriverHealth> CheckHealthAsync(CancellationToken token = default) => Task.FromResult(new DriverHealth(true, "ok"));
    public void Dispose() { /* 释放资源 */ }
}
```

## 6. 插件装载器（Plugin Loader）与运行时管理

### 6.1 关键设计点
- 使用 **AssemblyLoadContext(isCollectible: true)** 来加载插件，便于卸载与回收
- 为每个插件创建独立的 ALC（隔离依赖）
- Host 只持有 IProtocolDriver 接口引用，但关联到 ALC 以便卸载
- 管理插件版本、状态、失败重启策略

### 6.2 Loader 功能概览
- `ScanPlugins(directory)`：扫描目录获取最新版本插件
- `LoadPlugin(path)`：创建 ALC，LoadFromAssemblyPath，解析类型并 CreateInstance
- `InitializePlugin(IProtocolDriver driver, DriverContext ctx)`：注入 context 并初始化
- `UnloadPlugin(pluginId)`：Dispose driver -> ALC.Unload -> 等待 GC 回收（推荐触发 GC）
- `ReloadPlugin(pluginId, newPath)`：Unload + Load

### 6.3 内存回收提示
- ALC 卸载后，需要等待 .NET 回收托管内存及释放 native handles
- 可通过 `WeakReference` 监控 ALC 回收情况并在超时后报警

## 7. 热更新（Hot Reload）流程

### 7.1 流程概述
1. 管理端上传新版本 DLL（或管理员放置到指定 plugins 目录）
2. Host 接收上传并将新 DLL 保存到 `plugins/<protocolName>/<version>/`
3. Host 停止调度到旧插件（或等待当前任务完成），标记旧插件为 `draining` 状态
4. Host 调用 `UnloadPlugin(old)`（Dispose + ALC.Unload）
5. Host LoadPlugin(newPath) 并 Initialize
6. 切换路由到新插件
7. 记录版本切换日志与回滚点

### 7.2 零停机注意点
- 在替换期间，短时间内可能并发存在新/旧两个实例，但 Host 应保证请求只路由到目标实例
- 对于长连接/会话型插件（例如 S7 的连接），应设计 `session draining`：新会话使用新插件，旧连接继续处理到完成再断开

### 7.3 回滚策略
- Host 保留至少 N 个历史版本（可配置）
- 回滚即 LoadPlugin(oldVersion) 并切回流量

## 8. 自动发现策略

### 8.1 插件目录规范
```
/plugins
  /modbus/1.0.0/Modbus.Driver.dll
  /s7/2.0.1/Siemens.S7.dll
  /fins/1.1.0/Omron.Fins.dll
```

### 8.2 扫描机制
- Host 在启动时扫描 `plugins` 目录加载默认版本
- 支持文件系统 Watcher（FileSystemWatcher / inotify）监听新增或修改
- 提供 REST API：`POST /api/plugins/upload` 上传插件、`POST /api/plugins/reload` 热更新

### 8.3 版本解析规则
- 优先加载 semver 的最大版本
- 名称/元信息解析：插件内部应提供 `PluginManifest.json` 或 `Assembly` attribute

## 9. 部署与跨平台注意点

### 9.1 Docker
- 将 `plugins` 挂载为一个卷（PVC）以便热替换
- 推荐把 Host 作为无状态服务，插件存放在外部卷

### 9.2 Kubernetes
- 使用 PVC 或者 Sidecar 同步插件目录
- 也可采用 Operator：当 Operator 接收到新插件时，调用 Host 的管理 API 上传插件/触发 reload

### 9.3 Windows / Linux
- 文件路径、权限、共享库（native libs）差异需考虑
- 若插件需要 native 依赖，建议使用 nuget/native bundle，并在部署文档注明

## 10. 安全与沙箱策略

### 10.1 插件来源验证
- 签名校验：建议上传时校验 DLL 签名或提供签名证书
- 白名单/黑名单：控制允许的插件提供方

### 10.2 权限控制
- Host 提供最小化 Host API（只暴露必要能力）
- 使用 ACL 控制插件可以访问的资源（文件、网络）

### 10.3 运行时隔离
- 限制插件线程池/任务超时
- 捕获插件异常，确保不会崩溃 Host
- 监控插件的内存/CPU 占用，异常时自动隔离或重启

---

## 11. 日志、监控与健康检查

- 插件必须使用 Host 提供的 ILogger（便于集中化）
- Host 定期调用 `CheckHealthAsync` 并上报到监控系统（Prometheus/Grafana）
- 插件运行时发送 metrics（请求数、成功率、平均耗时）
- Host 提供 `/metrics` 与 `/health` HTTP Endpoint

---

## 12. 测试策略

- 单元测试：插件逻辑（不依赖 Host）
- 集成测试：Host + 插件（在独立 ALC 下运行）
- E2E 测试：Host 在容器中加载插件，通过真实或模拟设备进行通信
- 灰度发布：先对少量设备下发插件，观察后再全量

---

## 13. CI/CD 与发布流程

- 插件仓库采用 semver
- CI：构建 DLL -> 运行单元测试 -> 生成 artifact -> 签名 -> 上传到插件仓库（或提供管理员下载包）
- Host 管理端提供插件仓库配置（URL）以便自动拉取更新

## 14. 示例：Modbus / MC / FINS / S7 插件实现要点

### Modbus
- 使用 NModbus 或自行实现 MBAP/RTU 打包
- 支持多种 Endian、16/32/float 组合解析

### Mitsubishi MC
- MC 协议有 Frame、SubHeader、Command/Response，注意抓包对齐
- 注意三菱分为 MC Protocol (ASCII/BINARY/3E Frame)

### Omron FINS
- FINS 包含服务 id、address area、node 等
- 注意 IP 和 FINS node 的对应关系

### S7（建议使用 Snap7 / S7.Net）
- 建立连接管理，处理 TPKT/COTP/S7 PDU
- 插件中实现 DB/Area/Offset 的解析
- 对复杂 Struct 提供模板化映射（optional）
